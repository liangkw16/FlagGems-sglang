## 2. 工作流经验（最核心的复用资产）

1. **账本 + 证据链是一切的基石。** 每题一份 `experiments/*.md` 账本，
   预注册假设、逐芯 speedup、提交号与 ZIP 哈希全部落盘；负结果照样入账
   （T28 六投换来"内容侧无解"的结论也是资产）。多会话并发靠账本防双写，
   以不可变提交记录为唯一真相源。
2. **门禁三件套 + 一次性 nonce 提交。** 源码锁 commit → 远端代理验证 →
   从 Git 对象重建 release 出不可变 ZIP 双端验 SHA → 实时 preflight 全绿
   才执行一次性 submit；`sending / uncertain / stale_after_upload` 状态
   绝不重试（HTTP 503、成功码 202 非 200 等场景多次靠这条避免重复扣额度）。
   同字节重掷上限 2 次，用于区分平台抖动与 kernel 问题。
3. **单变量纪律 + 预注册晋级/止损门。** 每个 ZIP 只改一条芯路径（曾逐
   成员比对抓出"P0 包实际改了 3 条路径"的事故）；离线几何均值 ≥1.05~1.08
   才投；预算写死（每题 2~5 发硬上限 + 留 20% 给"均值门失败但芯片信号
   为正"的重开）。反例：第四批最后 10 发中 8 发是无预注册收益的重复测量，
   14:40 耗尽额度且零名次提升。
4. **分工模式：远端后台 + 前台并行。** GPU 验证远端后台跑（screening/
   release/resource audit 三件套 + watcher 轮询回填），前台继续只读审计
   和调研；只读查询不连远端、不耗额度。信号驱动 cron 只读监控（昆仑
   达标数/榜单异动）满足预注册条件才动封存弹药。
5. **坑当场沉淀进 skill。** 每踩一个坑就写进 skill 硬事实表或账本 INDEX，
   多个会话冷启动都能靠 skill+账本复现全流程——这是极短用户指令
   （"继续/开工/记录一下"）能持续推进的原因。

## 3. 跨芯片技术规律（平台实证，均已多题验证）

| 芯片 | 关键事实 |
| --- | --- |
| 燧原 GCU | i64 IR 是编译失败第一根因（索引全面 int32 化可救）；grid.y≤255、物理并行约 12 CTA；dot 需 64/64/128+stages≥2；pointwise 大 tile 单调升至 32K，reduction 峰值 8192；官方默认 launch 有时反快 +38% |
| 昆仑 XPU | 本季最大阻塞源：compile-worker 1830s 崩溃族（与提交字节无关，同指纹不重试）；BLOCK 是唯一有效调参轴（warps/stages 为 invalid 参数）；忌间接寻址混 dot、split-K、动态循环——解药是 host 物化边界→规则小核→逆写回；删"恒真 mask"会静默损坏（idle core 越界写）；`uni_sram` 报错是任意 pass 失败的统一包装，别只缩 tile |
| 昇腾 | coreDim≤65535（capped grid-stride 七次验证有效，cap 值要扫）；UB 1,572,864 bits 锁死 tile；flash 类必须 `num_vectorcore` 物理 worker；低精度 Cube dot 可迁移（6.4 倍收益） |
| 天数 | fp32-ieee dot **静默算错**（错误指纹恒定），须 fp16 操作数或 split-fp16——与昆仑恰好镜像 |
| 其他 | 海光 autotune 与 kwarg 双重绑定会 TypeError（BLOCK 走位置参数）；沐曦信官方 launch policy 的形状档；card_a 选 `_nvidia` 后缀、card_b 按 `_amd` 建 fallback |

**dtype 兼容矩阵是最值钱的一张表**（详见 retrospective §2.8）：generic
低精度 dot 必须配昆仑 fp32 回退 vendor，逐题验证不可想当然（T58 与 T12
结论相反）。

## 4. 判断与方法论纪律

1. **NVIDIA 代理只做灾难门，性能信号不可外推**——T24 代理 5x→燧原
   -24.5%、T16 代理 9.6x→实际 0.035x、T47 代理 12x→平台 2/2 编译崩溃，
   差两个数量级的例子反复出现。
2. **数学等价 ≠ 逐字节一致**："等价改写"多次被平台打回（E6r 回退精确
   字节 +82%）；语义等价的化简（删恒真 mask）也能静默损坏。
3. **先结构后调参**：T38 删一个 host 侧 `.item()` 同步（25µs 税）七芯
   几何均值 2.2x，胜过一切 tile 扫参；访存布局、重复计算、launch 开销
   查完再动 tile。
4. **归因要逐芯差分，均值会骗人**：T51 燧原 442x 占均分 91%；单芯增益
   会被冻结芯波动淹没；"num_warps 影响分数"这类相关性不能写成因果定论，
   失败只封具体候选不封整个方向。
5. **移植上游必须连调用方前提一起读**：T48 漏掉"调用方已切短 segment"
   契约，75% mismatch；边界覆盖 B-1/B/B+1、多 tile、非整除、stride、舍入。
6. **排行榜要用实时只读查询 + raw_result 通道**：CLI 会过滤失败详情，
   带 token 直取 `operator-submissions.raw_result` 的 errors/failed_cases，
   一行情报省一发额度（T47 昆仑 int32→long 根因即来自此）；快照会过期，
   榜首夜涨 33% 常见。
7. **测试门禁要真实加载**：AST/静态检查不 importlib 加载就是裸奔（T19
   海光 autotune 平台爆炸）；vendor 变体必须进同一测试矩阵，否则
   "generic 绿"掩盖风险。

## 5. Agent 协作经验（ZCode + Codex 双工具）

**好用的模式**：

- 极短用户指令 + skill/账本承载全部上下文；
- 并行只读子代理做审计/PR 扫描/code review（真实拦下过 grid 超限、测试
  入口错位等 P1 缺陷）；
- 用户只做 A/B 拍板和外部事实校准（"他队同窗口能过"一句话推翻过 agent
  的"平台墙"悲观结论）；
- Codex 的 goal 持续化 + 自动提交授权支撑了 T36 连打 20 发的超长闭环；
- 远端 GPU 后台验证 + 前台并行调研的分流是高产关键。

**校准过的坑**：

- Codex 咨询的结论必须逐条对源码核实（"说改 2 条实为 3 条"、
  `isCloseCoreTiling` 语义反转等多例）；
- KernelGen/MCP 只当结构 oracle——`passed=true` + 测试数 0 一律不信、
  昆仑 verifier 502 是服务端故障；唯一硬价值是"失败神谕"（error 带
  raised 链 = 真机编译失败，可零额度预筛 NPU vendor）；
- 并发会话会抢提交（审计说"勿投"时 E5 已发出），要以账本协调；
- Codex goal 续跑每轮都触发 skill 重复收口 8+ 次，应设"无 diff 不重审"；
- agent 的全局止损结论（"0 题值得重开"）系统性偏悲观，需要外部证据校准。

## 6. 事故级教训

1. **OPSEC（08-26）**：研究分支误推公开 fork 暴露 1.5 天。此后赛中
   研究分支/账本严格控制 push 目标；开赛前 `git remote -v` 体检；PR 只
   在官方窗口从干净分支发。fork 推送策略如调整，须显式记录决定与理由。
2. **门禁工具自身也要 review**：曾发现 `stale_after_upload` 可重投、
   注释载体改 SHA 绕过去重等 5 项工具自身缺口。
3. **平台侧故障与提交字节无关**：system_failed / pending_challenge /
   评测停摆不为相同字节重传，出路是工单；昆仑崩溃族同指纹绝不重试。

## 7. 对当前阶段的直接行动建议

1. 额度预算先于发射：每发写清假设、受影响芯片、晋级门与止损条件；
   无预注册收益的重掷一律转为防御储备。
2. 开局即逐芯差距分析（raw_result + 逐芯榜单），按"预期均值增量"而非
   "最慢芯相对提升"排投发顺序。
3. 昆仑问题先判指纹：同字节前科对照 → 结构改造（物化→规则核→逆写回）
   → 工单；不为编译崩溃族烧重复字节。
4. Agent 结论分层采信：审计/取证可用，跨芯性能主张必须平台证据闭环；
   全局悲观结论要求外部事实校准后再执行。
